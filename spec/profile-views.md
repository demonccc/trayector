# Profile Views

Trayector separates **canonical career knowledge** from **derived presentation views**.

This distinction allows a profile to remain structurally consistent while presenting itself differently to humans, recruiters, AI systems, websites or generated résumés.

## Canonical knowledge

Canonical knowledge lives in the profile's structured documents and relationships, including:

- `profile/`;
- `experience/`;
- `projects/`;
- `deep-dives/`;
- `stories/`;
- `feedback/` when present;
- `content/`;
- `profile.json` for machine-readable navigation.

Profile configuration such as languages and classifications lives under `.trayector/settings/`. It helps tools interpret the profile, but it is not itself career knowledge.

These canonical files are the source material from which views can be built.

## README as the default human view

The repository `README.md` SHOULD be treated as the default human-facing profile index.

It SHOULD present the person and provide useful navigation into the canonical profile.

It SHOULD NOT be the place where the Trayector specification itself is explained in depth.

A README MAY include:

- professional introduction;
- current focus;
- capability highlights;
- selected projects or deep dives;
- career snapshot;
- selected content;
- feedback links;
- education links.

The README MAY repeat concise information from canonical documents when useful for presentation because it is a derived view, not an independent source of truth.

When canonical career data and the README disagree, canonical documents take precedence and the README SHOULD be regenerated or corrected.

## Tailored résumés as target-specific views

A résumé is another derived view of the same canonical career knowledge.

A tailored résumé MAY be generated for a specific job description, role family or application context by selecting, ordering, shortening and emphasizing the most relevant supported information.

The target role MAY influence:

- the professional summary;
- capability ordering;
- which experiences receive more detail;
- which older experiences are condensed;
- which projects, deep dives or publications are selected;
- presentation wording when the meaning remains faithful to canonical facts.

The target role MUST NOT create new facts.

A résumé generator MUST NOT invent unsupported dates, titles, seniority, technologies, metrics, certifications, leadership scope, ownership, outcomes or capabilities simply because the target role asks for them.

Résumé templates define presentation strategy and section shape. They do not define career truth.

Trayector provides a basic template and MAY provide additional templates for materially different presentation strategies such as architecture, engineering leadership or technical specialization.

See [Tailored Résumés](../docs/tailored-resumes.md).

## Trayector implementation reference

A profile MAY include `TRAYECTOR.md` as a small human-readable implementation note.

Its purpose is to:

- identify Trayector as the profile model;
- point to the specification;
- explain where the machine-readable entry point lives;
- clarify that the README is a view rather than the model itself.

`profile.json` remains the machine-readable declaration of the Trayector version and navigation entry point.

## Generated and committed views

A view does not need to be generated dynamically.

`README.md` can be committed to Git and maintained manually, generated by a future Trayector CLI, or produced by an AI-assisted workflow.

Tailored résumés can be ephemeral or committed under `generated/resumes/<target-slug>/` when keeping the application-specific output is useful.

Regardless of how a view is created, it SHOULD be reproducible from canonical profile knowledge plus explicit presentation choices such as the selected template and target role.

## AI-generated views

An AI generating or updating a README or résumé SHOULD:

1. read `profile.json`;
2. follow `trayector.instructions` and read relevant configuration under `.trayector/settings/`;
3. follow navigation into canonical profile areas;
4. read the target role when generating a tailored résumé;
5. summarize, select and reorder rather than invent;
6. prefer linked evidence for capability highlights;
7. avoid presenting unresolved or weak claims as facts;
8. use the selected presentation template as guidance, not as a source of career facts.

This keeps AI in the role of interpreter and compiler rather than source of professional truth.
